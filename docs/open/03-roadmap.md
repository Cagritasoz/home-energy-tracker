# Roadmap

What is planned and in what order, project-wide. A feature that has its own design document in `docs/design/` keeps its own roadmap there (the outbox's remaining steps are in `01-outbox-design.md`; the account-deletion saga's are all done, `03-account-deletion-saga.md` section 17); this file only points at them. When a step is done, it is removed or marked here in the same change that finishes it.

## Order of work

1. **user-service**, finished with real test coverage: the account-deletion saga is built and tested (`docs/design/03-account-deletion-saga.md`); the steps below remain.
2. **device-service**, rebuilt: device tokens, the compacted registry topic `device.registry.v1`, consuming `user.events.v1` (it is the first participant of the deletion saga and confirms with `UserDevicesUnclaimed` on `device.events.v1`).
3. ingestion-, usage-, alert-, notification- and ai-insight-service, then the gateway.

## user-service: remaining steps

In this order. Each step is placed where it is because of what comes before or after it: settings are typed before more settings are added, code and schema are cleaned up before the first deployment freezes them, runtime settings and metrics exist before there is a container to run, and the API is documented once it has stopped moving.

1. **Typed configuration.** Replace the scattered `@Value("${app.…}")` reads (35 in all, reading 32 distinct `app.*` keys, in constructors and `@Bean` methods) with `@ConfigurationProperties` classes (records, `@Validated`), grouped by feature: outbox, deletion, Keycloak admin, security, Kafka. A wrong or missing value then fails at start-up with a clear message, related settings sit together, and the IDE knows them. Includes moving the CORS allowed origins out of `SecurityConfig` into a setting. This comes first because every later step adds settings (timeouts, pool sizes, metrics, the container's environment), and they should land in typed classes instead of adding more `@Value`s. `04-conventions.md` (Configuration) changes in the same step.
2. **Code and schema hygiene, before the first deployment.** None of it changes behavior; all of it is cheaper before an environment holds data and before more code leans on it.
   - **Migration baseline.** Squash `V1`–`V14` into one baseline migration (the history has a schema reset in `V5` and creates `outbox_events` twice, in `V4` and `V7`). Allowed only while no environment but local development has applied the history; from the first deployment on a migration is never edited. Local databases are recreated; the documents that cite migration numbers (`02-user-service-status.md`, the saga design, section 5, the outbox and processed-events designs) are rewritten in the same change.
   - **Entities.** `User`, `OutboxEvent` and `UserDeletionParticipant` use Lombok `@Data`, whose `equals`/`hashCode` cover every mutable field; replace it with `@Getter`/`@Setter` and an `equals`/`hashCode` based on the assigned id. `04-conventions.md` (Entities) changes in the same step.
   - **Keycloak admin token.** Evaluate Spring Security's OAuth2 client (`OAuth2AuthorizedClientManager`, client-credentials) in place of the hand-written token cache in `KeycloakAdminRestClient`, which is the standard way to call another service with a service account and removes the `synchronized` around an HTTP call. If it holds up, adopt it (the circuit breaker and retry stay); if not, record why the hand-written one stays.
   - **Small guards.** A token validator for `sub` (must be a UUID, else 401 `invalid_token`) in the validator chain of `SecurityConfig`, so the rule sits at the trust boundary: today a malformed or missing `sub` ends in a 500 at the two places that parse it, reachable only with a token validly signed by Keycloak. A format check for `outbox_events.topic` (outbox design, section 13).
   - **Leftovers.** The commented-out clock-skew line in `SecurityConfig`, the TODOs in `UserProvisioningInterceptor`, `UserProvisioningService` and `GlobalExceptionHandler`, and the stray note in `DeletionFinalizationJob`.
   - **Event format decision.** Record in `08-design-decisions.md` why events use a hand-made envelope in a shared `contracts` module, and what would replace it (CloudEvents, or a schema registry with Avro or JSON Schema) if services are ever released independently.
   - **An ArchUnit test for the package rules** (proposed, not yet agreed): no cycles; `user`, `outbox` and `keycloak` depend on nothing above them; `security` stands alone; controllers only in feature packages. Possibly with tighter visibility (package-private classes). Last in this step, so it describes the structure the earlier items leave.
3. **Runtime configuration and observability**, in two parts, the first before the second:
   - *Runtime configuration:* `open-in-view: false` (Boot defaults it to true), Hikari pool sizes, database timeouts (`statement_timeout` in the JDBC URL, `lock_timeout`, `idle_in_transaction_session_timeout`, the JDBC `socketTimeout`, `tcpKeepAlive`), graceful shutdown. Then virtual threads. Two things to do with them: Boot then builds a different scheduler (the pool size property no longer applies), and the token methods of `KeycloakAdminRestClient` are `synchronized` around an HTTP call, which pins the carrier thread on JDK 21; replace the monitor with a `ReentrantLock` (not needed if step 2 moved the token to Spring Security's OAuth2 client).
   - *Observability:* the actuator `prometheus` endpoint and the service's metrics (outbox lag, parked count, age of the oldest `DELETING` account, the saga gauges), `logging.structured.format.console: ecs`, Micrometer tracing to Tempo with the trace id as `correlation_id` (open decision in `08-design-decisions.md`), the JWT `sub` as `userId` in the logging context. Then the alert rules, once something scrapes the gauges: `outbox.oldest.pending.age.seconds` above 60 s for 2 min (warn) and above 300 s (critical), `outbox.parked.rows` above 0, `outbox.relay.consecutive.failed.ticks` above 0 for 2 min (warn), `keycloak.admin.circuit.state` at 2 for more than a minute, a dead-letter alert per consumer topic.
4. **API documentation.** An OpenAPI description of the customer and admin APIs (springdoc), with the `ProblemDetail` error shapes, so a frontend or another service has a contract to read. The problem `type` URIs (`https://home-energy-tracker/problems/…`) either point at a page that explains each problem or are replaced by a documented scheme. After the security and error handling stopped changing (steps 1–3), before the admin write endpoints widen the API.
5. **Replay**: a `UserSnapshot` event (with fixture) and `POST /api/v1/admin/users/replay-snapshots`, so a new or lost consumer can rebuild its copy; outbox replay by aggregate id or `seq` range; the operator quarantine that uses the `parked` column. Needed by the time device-service starts consuming `user.events.v1`.
6. **Container**: a Dockerfile and a compose service with a readiness health check. After step 3, so the image starts with graceful shutdown, timeouts and a scrapeable endpoint.
7. **With the rest of the system**: load tests, to settle the relay's tuning and the cost of provisioning on every request (`UserProvisioningInterceptor` and the controller each read the user row); end-to-end tests (`e2e/`) once device-service consumes `user.events.v1`; the consumer half of the event contract tests (read a fixture, assert the handler's effect) with the first consumer.

## Planned, not yet scheduled

In this order, which is the order of their dependencies. None of them starts before the steps above.

1. **Retention for personal data in `user.events.v1`**: saga design, section 13. Mostly topic configuration (`retention.ms` matching the outbox purge, or crypto-shredding); due before the service holds real users' data.
2. **A reconcile of diverged emails and a reconcile of orphaned accounts**: saga design, section 13. They act on what the `user.email.token.mismatch` and orphan metrics report, so they follow the observability step.
3. **Recent-login check on `DELETE /me`**, which needs an `auth_time` claim in the access token (not present today; a Keycloak realm decision, open in `08-design-decisions.md`).
4. **Admin write endpoints** (create, patch and delete a user). They act on a target `{id}` through the same service methods as the customer endpoints. Creating a user means creating the Keycloak account first (the row's id is its `sub`), then the row; deleting is the saga with the deadline set to now; the events should record the acting admin.
5. **`If-Match` and 412 on `PATCH /users/me`**, deferred: today a stale write is caught by `@Version` and answers 409. Becomes worth doing with the admin write endpoints (admins edit other people's profiles), or with the first resource that clearly needs it (device or alert-rule edits), or if user-service becomes the reference pattern.
6. **Email change.** Needs notification-service. Agreed design: saga design, section 10.4. Until it exists an email cannot be changed.

Other services follow their own design documents when they are rebuilt.
