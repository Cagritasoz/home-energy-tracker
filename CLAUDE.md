# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`home-energy-tracker` is a learning project: four independent Spring Boot microservices tracking home energy consumption, wired together by Kafka events, one shared PostgreSQL instance (schema per service), and InfluxDB for time-series readings. Java 21, Spring Boot 4.1.1, Jackson 3, JUnit 5, Lombok.

**Maven reactor structure** (migrated from four standalone projects — see git history around 2026-09-15 for the restructure): one root `pom.xml` (packaging `pom`, parented on `spring-boot-starter-parent`) aggregates every module and holds the one Maven wrapper for the whole repo — services no longer have their own `mvnw`. Each service's `pom.xml` is parented on the root pom (`<relativePath>../../pom.xml</relativePath>`) and only lists dependencies, no versions. Layout:
- `contracts/` — plain jar (no Spring; only Lombok, compile-time) holding the shared vocabulary of the user/device events: `EventEnvelope<T>`, per-event data records (`UserRegisteredData` so far), `UserEventType`/`UserEvents` (event-type names, topic `user.events.v1`, aggregate type, producer name) and `EventHeaders`. Not yet used by any service, and only `UserRegistered` has a data record — `UserUpdated`/`UserDeletionRequested` data records are still to come. See "Kafka event contract" below.
- `services/user-service`, `services/device-service`, `services/ingestion-service`, `services/usage-service` — the four services below, unchanged except for their POM's `<parent>`.
- `infra/` — `docker-compose.yml`, `.env.example`, `.env` (gitignored, as before). **All docker-related services and their properties live here now, going forward** — postgres/keycloak/prometheus/grafana/tempo config, once any of those exist, join it here rather than at repo root. `infra/kafka/kafka-topics.sh` provisions Kafka topics that have no single owning service (see "Kafka event contract" below) — run once by the one-shot `kafka-topics-init` compose service (`--profile kafka`), same image as the broker, exits 0 by design.
- `e2e/` — Layer 4 cross-service tests (Testcontainers `ComposeContainer` against `infra/docker-compose.yml`). **Stub: builds, zero test classes yet.** Only enters the reactor under the `-Pe2e` profile, so a plain `./mvnw test` never touches it.
- Planned, not yet built: `services/alert-service`, `services/notification-service`, `services/ai-insight-service`, `services/api-gateway` (see Roadmap).
- `docs/design/` — the outbox (`01-outbox-design.md`) and `processed_events` (`02-processed-events-design.md`) design docs. They are a *direction*, not a spec: adopt what fits, adapt the rest (e.g. `V7` uses `outbox_events` and this project's `pk_/uq_/chk_/idx_` naming instead of the doc's `outbox`).
- `scripts/` — local-dev helpers. `get-token.ps1 -Role user|admin` prints a Keycloak access token for the seeded test/admin user (PowerShell; a `.sh` equivalent is not written yet).
- Root `pom.xml` `<dependencyManagement>` pins BOMs for Spring Cloud, Spring AI, Resilience4j and Testcontainers — imported for the modules above that need them once they exist; nothing consumes Spring Cloud/Spring AI yet.

**Design principle: model real IoT energy devices as accurately as reasonable**, not a convenient simplification. This has already driven one real design change — see "Reading model" in the Roadmap — and should keep informing future choices (e.g. device behavior, failure modes) over whatever is easiest to fake.

## Commands

### Infrastructure (from `infra/`)
```bash
cd infra
cp .env.example .env          # then fill in real values
docker compose up -d          # user-db, keycloak-db, keycloak - all user-service needs
docker compose --profile kafka up -d      # + kafka (KRaft) and kafka-ui (:8070)
docker compose --profile influxdb up -d   # + influxdb (usage-service only)
docker exec -it influxdb influxdb3 create token --admin   # one-time; export result as INFLUXDB3_AUTH_TOKEN
```
Or from repo root: `docker compose -f infra/docker-compose.yml --env-file infra/.env up -d`.
Each service's Flyway creates its own schema (`user_service`, `device_service`) on first run because `spring.flyway.schemas` is set; Flyway owns all DDL after that.

### Build (one wrapper, at repo root — services no longer have their own)
```bash
./mvnw clean package                                              # build + test every module (use .\mvnw.cmd in PowerShell)
./mvnw test                                                       # all tests, every module
./mvnw -pl services/user-service -am spring-boot:run              # run one service (-am also builds its reactor dependencies, e.g. contracts once used)
./mvnw -pl services/user-service -am test -Dtest='UserServiceApplicationTests#contextLoads'   # single test
```
`-pl services/<name>` targets one module from the root; equivalently `cd services/<name>` and run `../../mvnw ...` from there. `-Pe2e` activates the `e2e/` Testcontainers-ComposeContainer suite (stub module — no tests yet).

- **`.env` is only read by docker compose.** Running a service via `mvnw` needs `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` (and for usage-service `INFLUXDB3_AUTH_TOKEN`) exported into the shell — `application.properties` resolves them as `${...}`.
- **usage-service** requires `--add-opens=java.base/java.nio=ALL-UNNAMED` (InfluxDB 3 client's Arrow Flight SQL path). `spring-boot:run` injects it automatically; a packaged jar needs it passed to `java` directly.

## Architecture

### The reading pipeline
`ingestion-service` — via `POST /api/v1/ingestion` or the `@Scheduled` `ContinuousDataSimulator` (toggle `simulation.enabled`) — builds an `EnergyUsageEvent` and publishes it to Kafka topic `energy-usage-events`, keyed by `deviceId`. Publishing is fire-and-forget (telemetry latency must not wait on broker ack).

`usage-service` consumes on a single listener thread, tags each reading with `deviceKnown` (looked up in `DeviceIdCache`), and writes an InfluxDB `Point` (`energy_readings` measurement in the `energy_usage` database). A write failure propagates out of the listener so the container's `DefaultErrorHandler` retries, then routes to `energy-usage-events-dlt`. An **unknown deviceId is never dropped** — the cache is advisory and eventually consistent; dropping real telemetry over a stale cache would lose data.

### Kafka event contract (important)
Two generations coexist:
- **User/device events (new, outbox-based, `user.events.v1`): shared `contracts` module.** Decided 2026-09-26 because several services (device, alert, notification, ai-insight, user itself) consume them and hand-copied envelopes would drift. The wire format is plain JSON with **no Java class names and no `__TypeId__`**: the value is the serialized `EventEnvelope<T>` and consumers dispatch on `eventType` (also the `event_type` header). `eventType`/`aggregateType` are `String`s in the envelope, never enums, so a consumer survives a producer adding a new type; producers use the `UserEventType` enum and send its `value()`. Consumers read the envelope with `data` left as a tree, switch on `eventType`, then convert `data` to the matching record; unknown fields are ignored (plain Jackson 3 does this by default), unknown `schemaVersion`s go to the DLT. The cost of sharing: a breaking change to a record means every dependent service moves together (cheap in this one reactor). **Its topic is provisioned by `infra/kafka/kafka-topics.sh` (2026-09-27), not a Spring `NewTopic` bean** — `user.events.v1` has no single owning service (user-service produces; device/alert/notification/ai-insight-service all consume), so a bean-per-service would mean N copies of the same partition/replication config with nothing enforcing they agree. 3 partitions (bounds future parallel consumer instances per group; never affects per-user ordering, since the key is always `aggregateId`), replication factor 1 (this compose file runs one broker — raise the day a second one exists). No retention override yet; the broker default applies until replay actually needs a specific window.
- **`energy-usage-events` (ingestion-service → usage-service, older): each side keeps its own copy** of the event record; the wire contract is the logical alias in `spring.json.type.mapping` (`energy-usage-event`), written into the `__TypeId__` header; neither service depends on the other's packages. **Still a `NewTopic` bean in each service** (a deliberate exception to the rule above: this topic has exactly one producer and one consumer, so per-service beans don't have the multi-owner drift problem `user.events.v1` has) — left as is until that pipeline is reworked (cumulative-counter rename), at which point revisit whether it should move to the same script for one consistent story.
In both cases `ErrorHandlingDeserializer` wraps the delegate deserializers so a poison message goes to the DLQ instead of wedging the consumer forever. Apply this to every future topic. **Any future topic with more than one owning service goes in `infra/kafka/kafka-topics.sh`, not a bean**, following `user.events.v1`'s pattern.

### Cross-service coupling is deliberately minimal
- **No foreign keys across schemas.** `devices.user_id` has no DB FK — the relationship is enforced in code. (A FK *was* correct *within* a schema when `alert_rules.user_id → users.id ON DELETE CASCADE` existed — `alert_rules` is dropped for good as of `V5`, not pending redesign; alert rules move to their own dedicated service, not back into user-service. Apply the same intra-schema-FK-yes/cross-schema-FK-no rule if that new service ever owns a table with a comparable intra-schema relationship.)
- **REST calls have explicit timeouts** (`RestClientConfig` in device-service and usage-service). A hung dependency surfaces as `ResourceAccessException` → 503, never an exhausted thread pool.
- **`DeviceIdCache`** (usage-service) polls `GET /api/v1/devices/ids` every 30s into a `volatile` immutable snapshot; a failed refresh keeps the last good snapshot rather than wiping to empty.

### Identity (Keycloak)
`infra/keycloak/realm-energy.json` is imported into Keycloak automatically on first boot (`start-dev --import-realm`, mounted read-only) — it only imports into an *empty* Keycloak instance, so editing it requires `docker compose down -v` (dropping Keycloak's own storage) before the next `up` for the change to take effect. It pre-creates:
- Realm `energy-tracker`.
- Client `local-dev` (confidential, `directAccessGrantsEnabled` + `standardFlowEnabled` both on) — a **local-testing stand-in for the future api-gateway client**, not a real application. Its secret (`secret`) is committed in that file on purpose — it's a throwaway local-dev credential, not a real one; treat it like any other value in this repo's `.env.example`, not like the `.env`-only rule in Coding conventions' Secrets bullet.
- Admin user `admin@example.com` / `Adminpassword1` (realm role `ADMIN`, fixed id `22222222-2222-2222-2222-222222222222`) for `/api/v1/admin/**`.
- Test user `testuser@example.com` / `Testpassword1` (realm role `USER`), with a **fixed** id (`11111111-1111-1111-1111-111111111111`) so its Keycloak subject — and therefore `users.id` — stays the same across every `down -v && up` reset during local dev.

**Getting a JWT locally** (direct access grant — username+password straight to Keycloak's token endpoint, no browser):
```bash
curl -X POST http://keycloak:8180/realms/energy-tracker/protocol/openid-connect/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d grant_type=password \
  -d client_id=local-dev \
  -d client_secret=secret \
  -d username=testuser@example.com \
  -d password=Testpassword1
```
The response's `access_token` is the JWT; its `sub` claim is `11111111-1111-1111-1111-111111111111` — that's the `users.id` value a first `GET /users/me` call would need a matching row for. Send it as `Authorization: Bearer <access_token>` on requests to user-service.

**user-service side:** `spring-boot-starter-security-oauth2-resource-server` (see the pom.xml comment — Boot 4.1.1 deprecated the non-`security-`-prefixed artifact name in favor of this one) + `spring.security.oauth2.resourceserver.jwt.issuer-uri=http://keycloak:8180/realms/energy-tracker` (the host name `keycloak` must resolve on the dev machine: add `127.0.0.1 keycloak` to the hosts file, because Keycloak's `KC_HOSTNAME` pins the `iss` claim to that URL) + a `SecurityConfig` requiring authentication on every request, `/api/v1/admin/users/**` restricted to realm role `ADMIN`, and an audience check for `user-service`. None of this has been tested end-to-end against a running Keycloak yet.
**Audience:** `local-dev` carries an audience mapper that adds `user-service` to `aud` (Keycloak's default is only `account`), and user-service rejects tokens without it. Revisit once api-gateway exists and multiple services need to trust *different* audiences from the same realm.
**Port 8180, not Keycloak's own default 8080** — 8080 is already user-service's port (see the service table above).

### Persistence
- One Postgres instance, **schema per service** (`currentSchema=` in the JDBC URL + `spring.flyway.schemas`), each with its own `flyway_schema_history`.
- **`spring.jpa.hibernate.ddl-auto=validate`** everywhere — entities must match the Flyway-managed schema exactly. Schema changes are **new forward migrations** (`V2…`, `V3…`); never edit an applied `V` file (checksum mismatch fails startup).
- Audit columns (`Instant` ↔ `TIMESTAMPTZ`): user-service lets **the database own time** — `created_at DEFAULT CURRENT_TIMESTAMP` (`V5`) plus a `BEFORE UPDATE` trigger stamping `updated_at` (`V6`), mapped with `@Generated` (`insertable = false, updatable = false`) so Hibernate never writes them and every writer (Hibernate, native SQL, psql) gets the same clock. The trigger deliberately leaves `version` alone: Hibernate's `@Version` owns it, and native `UPDATE`s must still do `version = version + 1` themselves. Services not yet rebuilt (device-service, etc.) still use `@CreationTimestamp` / `@UpdateTimestamp`.

### Web layer conventions
- Each web service has one `@RestControllerAdvice GlobalExceptionHandler` returning `ProblemDetail`. Typed domain exceptions: `*NotFoundException` → 404, `Duplicate*Exception` → 409, `ResourceAccessException` → 503, `MethodArgumentNotValidException` → 400 with a field-keyed `errors` map, `HttpMessageNotReadableException` → 400. `user-service`'s handler is the reference implementation: it extends `ResponseEntityExceptionHandler` (so Spring's own MVC errors are ProblemDetail too), gives every error the same fields as the security handlers' 401/403 (`type` under `https://home-energy-tracker/problems/`, `title`, `status`, `detail`, `instance`, `timestamp`), maps `OptimisticLockingFailureException` → 409, and has a catch-all 500 that logs the cause instead of returning it (it rethrows `AccessDeniedException`/`AuthenticationException` untouched, so a `@PreAuthorize` denial still reaches `ExceptionTranslationFilter` and the 401/403 handlers in `SecurityConfig` instead of becoming a 500).
- DTOs are Java **records** with `@Builder` and `@JsonPropertyOrder` (Jackson 3 orders alphabetically by default; it also matches JSON keys to field names **verbatim** — no snake_case conversion, so field names must be the exact wire names in camelCase).
- Bean Validation annotations live on request DTOs; `@Valid` on the controller parameter.
- `user-service` / `device-service` have AOP aspects: `LoggingAspect` (service method entry/exit/throw) and `ExecutionTimeAspect` (controller timing). These are log lines only, not exported metrics. Any method invoked on a fixed timer regardless of whether there's anything to do (`OutboxRelay.relay()`, and the `OutboxService` methods it calls every tick) should carry `@SkipLogging` (`user_service.aspect`) rather than be left to `LoggingAspect`'s default package-wide pointcut — each invocation there isn't a meaningful event the way a request-driven method's call is, unlike e.g. `OutboxService.recordEvent` (one call per real user action), which stays logged. Apply the same annotation to any future scheduled/polling method in a service that has a `LoggingAspect`.

### Uniqueness enforcement (the standard pattern here)
Application-level `existsBy…` pre-check for a clean 409 **plus** a DB unique constraint as the real guarantee (races that slip past the pre-check hit the `DataIntegrityViolationException` handler). user-service currently has no pre-check: accounts are only created by `UserProvisioningService`, where a clash on `uq_users_email` surfaces through that handler as a generic 409 (see the email TODO there).

## Coding conventions (respect these when making changes)

- **Comments.** This is a learning project — heavy explanatory comments are intentional and stay until the final product. Explain non-obvious decisions and anything the user may not already know. Do not strip comments as "cleanup."
- **Entities.** Lombok `@Data @Builder @NoArgsConstructor @AllArgsConstructor`. Any field with a default value needs `@Builder.Default`, or the builder path writes `null` into a `NOT NULL` column. Exclude lazy `@ManyToOne` fields from `equals`/`hashCode`/`toString`.
- **Config.** `@Value` into `@Bean` factory methods (`RestClientConfig`, `KafkaTopicConfig`, `InfluxDBConfig`); topics are declared as `NewTopic` beans (broker auto-create is off).
- **Secrets** stay in `.env` (gitignored). Never hardcode credentials or paste tokens into code/commits.
- **Never call a `@Transactional` (or otherwise AOP-advised) method via plain `this.` from inside its own class.** Spring implements `@Transactional`/`@Scheduled`/aspect advice via a proxy wrapping the bean; a self-invocation bypasses that proxy entirely, so the annotation silently does nothing - no error, just quietly-wrong behavior (this actually happened: `OutboxRelay` self-calling its own `markPublished` meant `published_at` was never really persisted, so every tick would have re-published the same rows forever - fixed by moving that method onto `OutboxService` and calling it as a genuine cross-bean call). If a method needs its own transaction/advice, put it on a different bean and call it from there.

## user-service — status: self-service and admin read APIs implemented; eventing and the deletion finalizer not built yet

The CRUD-+-outbox build described in earlier versions of this file (`V1`–`V4`) was manually verified end-to-end and worked — but user identity was an app-generated `BIGSERIAL`, which doesn't survive fronting the system with Keycloak: the id a JWT's `sub` claim carries has to be the id every service uses, or every service needs an id-mapping lookup that doesn't otherwise need to exist. `V5` (2026-09-15) resets the schema around that: `users.id` is now the Keycloak subject (`uuid`, never DB-generated), plus a three-state soft-delete lifecycle (`status` `ACTIVE`/`DELETING`/`DELETED`, `deletion_requested_at`/`deleted_at`, `devices_deleted` as a saga-completion flag) and a `version` column doing double duty as JPA optimistic-locking *and* the event `aggregateVersion` once eventing is rebuilt. Every column's reasoning is in `V5`'s own comments — don't duplicate it here, read the migration.

**This was a deliberate, scoped decision, not a start-from-nothing reset:** `outbox_events` (whose `aggregate_id`/`partition_key` can't stay a single `BIGINT` once the user id it carries is UUID) is dropped in the same migration rather than patched, since its UUID-native shape hasn't been designed yet. It — plus a new `processed_events` table for idempotent event consumption — comes back in a later migration once that design exists; don't guess at its shape ahead of that. **Update (2026-09-26):** `outbox_events` is back in `V7__create_outbox_events_table.sql` — table only, no Java yet (no entity, writer or relay); every column is explained in that file's comments. `processed_events` is still to come, with user-service's first consumer (`UserDevicesDeleted`). `alert_rules` is also dropped, but **permanently, not pending redesign** — alert rules move to their own dedicated service in the new design and have no future in user-service at all. Every `AlertRule*` class (entity, repository, service, controller, DTOs, exceptions, `AlertScope`/`EvaluationWindow`, the `ALERT_RULE*` outbox enum values) has already been deleted from this codebase, not just left to go stale — see git history around 2026-09-16.

**Current state of the Java code (matches the `V5`/`V6` schema; `V7`'s `outbox_events` table has no entity or code yet).** `User` maps the new `users` table; the legacy `OutboxEvent` entity, its repository, `OutboxService` and `OutboxRelay` are deleted (Hibernate's `ddl-auto=validate` would otherwise fail startup on the dropped `outbox_events` table), as is `UserRequest`. Orphaned and still to be removed or redesigned with the outbox: `OutboxAggregateType`/`OutboxEventType`, `UserChangedPayload`/`UserDeletedPayload`, and the unused `spring.kafka.*` / `app.outbox.*` properties. Accounts are created only by `UserProvisioningService` (just-in-time, via `UserProvisioningInterceptor`, which runs on every `/api/**` request - see "Cross-cutting: provisioning on every request" below); `UserService` covers `GET`/`PATCH`/`DELETE` on `/api/v1/users/me` (`DELETE` = `markDeleting`, an atomic native `ACTIVE`→`DELETING` compare-and-set using DB time) and `UserAdminService` covers the admin reads.

**API surface.** Implemented: `GET`/`PATCH`/`DELETE /api/v1/users/me` and admin `GET /api/v1/admin/users` (paged, fixed sort `createdAt DESC, id`, `size` ≤ 100) and `GET /api/v1/admin/users/{id}`. Not implemented: admin `DELETE`, the deletion finalizer (Keycloak disable, device-cleanup ack, `DELETING`→`DELETED`), outbox events. `userId` comes from the validated JWT's `sub` for `/me`; see "Identity (Keycloak)" for how requests authenticate.

**Cross-cutting: provisioning on every request.** `UserProvisioningInterceptor` runs `UserProvisioningService.ensureUsable` before every `/api/**` controller, not only `GET /users/me` - a frontend can't be trusted to always call a specific "provision me" endpoint first, so every request does it instead. Two side effects piggyback on this same pass rather than needing their own polling or a Keycloak webhook: `email` is re-synced from the token's `email` claim whenever it differs from the stored value (`UserRepository.syncEmail`, a native compare-and-set - see its comment for the concurrency reasoning) and only when `email_verified` is true, and `displayName` is seeded once at provisioning time but never re-synced afterwards (the app owns it after that). No `.env` field is trusted for identity beyond what the validated JWT itself carries.

**Also done alongside the schema reset:** Keycloak is running in `infra/docker-compose.yml` and user-service has resource-server wiring (`SecurityConfig`, `issuer-uri`) requiring a valid JWT on every request — see "Identity (Keycloak)" above. This is infrastructure/security wiring only; it has no endpoint to protect yet.

**What's preserved from before, for when eventing is rebuilt (read, don't re-derive from scratch):** the outbox pattern's actually-reliable properties (`recordEvent` joins the caller's transaction, `published_at` only set after a confirmed Kafka ack, relay stops the batch on first failed send, consumers filter on Kafka headers rather than deserializing everything) and the one real bug already found and fixed once (`OutboxRelay` self-invoking `markPublished` via `this.` silently bypassed Spring's transactional proxy — see Coding conventions' self-invocation rule) are exactly the kind of mistake worth not re-making when `outbox_events` comes back.

**Topic declaration removed (2026-09-19):** user-service's `KafkaTopicConfig` (the `NewTopic` bean for `user-domain-events`) is deleted — the topic layout is being redesigned. `OutboxRelay` is deleted too, and broker auto-create is off, so nothing creates or publishes to that topic anymore until the redesigned topic is declared again. The Config convention above (topics as `NewTopic` beans) still holds for ingestion-service and usage-service, which keep their own `KafkaTopicConfig`.

**Known gaps carried forward:** automated test coverage is still minimal - see Testing strategy; `trace_id`/`correlation_id` still project-wide-not-started (design agreed, see "Correlation id tracing: decisions" below — not built yet); `LoggingAspect` still has no field-level redaction (was flagged against `OutboxService.recordEvent`'s payload logging — moot until outbox eventing is rebuilt, but the aspect gap itself is unrelated to this reset and still real).

## Outbox and account-deletion saga: decisions (2026-09-26 — bring these up when the work reaches them)

Agreed in discussion, **none of it built yet** except the `V7` table. Whoever picks up the matching piece of work should remind the user of the relevant points below *before* coding it — the user asked for exactly that.

**Events (user-service emits three).** `UserRegistered`, `UserUpdated`, `UserDeletionRequested`. The state-carrying two send a **full snapshot**, not a delta, so a consumer's projection (e.g. notification-service's `user_contracts` table) can just upsert, guarded by `aggregate_version`. `UserDeletionRequested` is written in the same transaction as `ACTIVE`→`DELETING`; it replaces the earlier name `UserDeleted`, which would wrongly suggest status `DELETED`. No final `UserDeleted` event until a consumer actually needs "saga finished" (Kafka orders per key and a `DELETING` user can't produce more events, so nothing can arrive after the request).

**Who reacts.** device-service deletes the user's devices and emits `UserDevicesDeleted` (`aggregate_version` null, `causation_id` = the request event's id). alert-service deletes the user's rules; notification-service purges the user's projected PII (email). user-service **waits only for device-service** (`devices_deleted`); the rest are eventually consistent, so `DELETED` may precede their cleanup. Waiting for more services later means more flags beside `devices_deleted`.

**Deletion is irreversible.** No cancel endpoint, no grace period (a strong warning belongs in the client; a recent-login check is an optional API-side safeguard). `V5`'s comment on `idx_users_deleting` mentions a "grace period" — now inaccurate, but an applied migration can't be edited; the index still serves the stuck-deletion watchdog below.

**Saga duration is unknown and must not matter.** Outbox → Kafka → consumer retries make it durable; `DELETING` is a stable state. Never force `DELETED` because a service is slow. Build a watchdog that flags `DELETING` users older than a threshold, and use the outbox replay reset to re-emit a lost `UserDeletionRequested` (consumers are idempotent).

**Email tombstone (recommended, not built).** In the *same atomic UPDATE* that moves `ACTIVE`→`DELETING`, overwrite `users.email` with `deleting-<id>@invalid` (matches the status at write time — not `deleted-`, that's `DELETED`; it must still satisfy `chk_users_email`). This frees `uq_users_email` immediately, no index change needed. `displayName` is **not** touched here.

**`displayName` (recommended, not built).** Scrub it only at finalization (`DELETING`→`DELETED`), not at the `DELETING` step. Unlike email, no unique constraint needs it freed early, so there's no urgency argument — only a privacy one, and it's outweighed by keeping the real name visible to whoever investigates a `DELETING` row stuck past the watchdog threshold. Use a fixed placeholder (e.g. `"Deleted user"`) satisfying `NOT NULL`.

**Keycloak (recommended, not built; revised 2026-09-27 — the first version below undercounted a real gap).** Original plan was one Keycloak DELETE, once, at finalization. Gap: that leaves the *real* email live on the Keycloak user for the entire `DELETING` window (which is explicitly unbounded — see the watchdog above), so a brand-new signup with that exact email is blocked by Keycloak's own uniqueness check even though our own `uq_users_email` already released it. Fix: two independent steps, neither synchronous inside the request (resilience4j retry/backoff adds real latency; `DELETE /me` must stay fast regardless of Keycloak's health) — both run from a small background poller instead:
- **Step 1, once `DELETING`:** one combined Keycloak Admin API call — disable *and* set the Keycloak email to the same tombstone value, in a single update request, not two. Marks `keycloak_disabled_at` (the `V5` column; this design gives it back its literal meaning) on success.
- **Step 2, once `devices_deleted = true`:** delete the Keycloak user entirely (not just disable — a disabled user still owns its email in Keycloak, whose realm rejects duplicate emails by default; unverified for this realm). Treat "already gone" (404) as success.
Step 2 does **not** wait on step 1 — deleting a still-enabled Keycloak user works identically to deleting an already-disabled one, so the two steps stay independent rather than chained; `keycloak_disabled_at` only records step 1, it doesn't gate step 2. Move to `DELETED` once step 2 succeeds and `devices_deleted` is true. Consequences: an already-issued access token stays valid until it expires regardless (JWTs are checked by signature), so the immediate lockout is still the interceptor's `AccountNotActiveException`, not Keycloak; user-service needs a service-account client with manage-users in `realm-energy.json` (Admin API details unverified). Both steps should share one resilience4j circuit-breaker/retry config, since what's being protected against is "Keycloak is down," not "this one operation is failing."

**Before the outbox writer is coded.** Each native writer must report whether it changed a row and, for events, the new `version`: `insertIgnoringConflict` and `syncEmail` return `void` today (`markDeleting` returns a count but not the version). Only the request that actually wins may emit its event (`UserRegistered` only from the insert that wasn't a no-op). Existing unit tests that stub these methods (`UserProvisioningServiceTest`, `UserServiceTest`) get small edits: an `OutboxService` mock, the new return values, and "loses the race, emits nothing" cases. `aggregate_version` will have gaps (version bumps that emit nothing, e.g. the `devices_deleted` flip): consumers compare with `>`, never `previous + 1`. `occurred_at` must equal the payload's `occurredAt`, so the app supplies it — take it from the aggregate row's own DB-stamped `created_at`/`updated_at` to keep the database as the owner of time.

**Before the relay is coded.** One active publisher via `pg_try_advisory_xact_lock` (cheap insurance at one instance, required at N: two relays would duplicate sends and interleave one user's events). `FOR UPDATE SKIP LOCKED` was rejected — it scales throughput but breaks per-aggregate ordering. Decide a policy for a permanently failing row: as designed the relay stops at the first failure, so one oversized message blocks the whole outbox forever; `attempts` alone has no cutoff. The lock is held across the Kafka sends, so bound the batch size and send timeout. Replay and dedupe interact: a replayed event keeps its `id`, so a consumer that already processed it drops it (and the equal `aggregate_version` fails the stale check) — replay only helps consumers that never applied the event; a projection *rebuild* needs the consumer to clear its `processed_events` rows for that handler. Keep `@SkipLogging` on the relay's scheduled method and never call its transactional helpers via `this.`.

**Before the finalizer is coded (resilience).** Resilience4j fits both Keycloak Admin API calls above (timeout, retry with backoff — both calls are idempotent, safe to retry — and a circuit breaker); user-service has no other synchronous dependency. Never hold a DB transaction open across those retries: read candidates, call Keycloak outside the transaction, then compare-and-set the state. **Verified 2026-09-27** (was previously unverified): `io.github.resilience4j:resilience4j-spring-boot3` (via the `resilience4j-bom:2.4.0` already pinned in the root pom) resolves and compiles cleanly against `spring-boot-starter-parent:4.1.1`, confirmed in an isolated scratch module — but it needs `spring-boot-starter-aspectj` for the annotation-driven proxying (`@Retry`, `@CircuitBreaker`), not the older `spring-boot-starter-aop`, which Boot 4 no longer manages (same rename pattern as the OAuth2 resource-server starter); user-service already depends on `spring-boot-starter-aspectj` for `LoggingAspect`, so no new AOP dependency is needed. Only compile-time compatibility was checked — starting an actual Spring context to confirm the AOP interception fires at runtime is still open. Spring Framework 7 also ships a built-in `@Retryable`, but since a circuit breaker is needed regardless, resilience4j alone (not a mix of two retry mechanisms) is the simpler choice.

**Before `processed_events` is added.** Build it with the first real consumer. user-service's own consumer (`UserDevicesDeleted`) is a flag flip made idempotent by a state guard (`WHERE status = 'DELETING'`); it must also ignore that event for users who are `ACTIVE` or already `DELETED`. The event has no `aggregate_version`, so idempotency there rests on the event id plus state guards.

## Correlation id tracing: decisions (2026-09-27 — agreed, not built yet; user wants to implement this)

Addresses the "`trace_id`/`correlation_id` still project-wide-not-started" gap under user-service's Known gaps. `outbox_events.correlation_id`/`causation_id` and `EventEnvelope`'s matching fields already exist but nothing populates them today — every `OutboxService.record*` builder call leaves them null.

**`correlation_id` vs `causation_id` — different jobs, different plumbing.** `correlation_id` stays the *same* value across an entire causal chain (one HTTP request → every event and every consumer's reaction to it) — it answers "which user action is this part of?" `causation_id` points to the *one* specific event immediately before this one — it answers "what directly triggered this?", and is null for anything caused by an HTTP request (nothing "caused" a human clicking delete). Because of that difference: `correlation_id` needs to flow silently through a whole request without every method signature carrying it, so it goes through MDC (SLF4J's thread-local diagnostic-context map — `MDC.put/get/remove`; already on the classpath via `logback-classic`/`slf4j-api`, confirmed 2026-09-27, no new dependency — and a logback pattern like `%X{correlationId}` prints it on every log line automatically, no per-call-site changes needed). `causation_id` is only ever known explicitly, at the one call site where a consumer is reacting to a specific message it just deserialized, so it stays a plain parameter, never an MDC value.

**How `correlation_id` gets wired (buildable entirely within user-service today).** A new, small `OncePerRequestFilter` (a separate class from `UserProvisioningInterceptor` — "who is this user" and "tag this request for tracing" are different concerns), generating a UUID at the start of the request — check for an incoming `X-Correlation-Id` header first and only generate one if absent, so a future api-gateway or any caller wanting end-to-end tracing can supply its own and have it honored. Put it in MDC (`MDC.put("correlationId", id)`), clear it in a `finally` (same class of bug as `SecurityContextHolder` leaking across pooled threads if not cleared — see `UserControllerTest`'s `@AfterEach clearSecurityContext()` for the identical pattern already in this codebase), and echo it back as an `X-Correlation-Id` response header. `OutboxService` reads MDC (a small private helper, null if absent) when building each envelope's `.correlationId(...)` — the calling code (`UserService`, `UserProvisioningService`) never needs to know this exists. **Unverified:** getting this filter to run *before* Spring Security's own filter chain (so even a 401/403 gets a correlation id in its own log lines) needs an explicit ordering — Spring Security's exact registration precedence should be checked empirically when this is actually built, not assumed as some specific `@Order` value ahead of time.

**`causation_id` and cross-service correlation propagation (only exercisable once a consumer exists).** A future consumer (e.g. device-service reacting to `UserDeletionRequested`) should, on receiving a message: set its *own* MDC `correlationId` to the *incoming* event's `correlationId` (not a fresh one — this is what keeps one correlation id constant across the whole saga, across service boundaries), then pass the incoming message's `eventId` as `causationId` when it emits its own new event(s). Nothing about any of this needs a schema or `EventEnvelope` change — both already have the fields; it's purely (a) the new filter, (b) a small MDC-reading helper in `OutboxService`, (c) an optional `causationId` parameter added to the `record*` methods for when a future consumer needs it.

## Structured logging and the observability stack (2026-09-27 — deferred until after correlation id tracing is built)

Ecosystem clarification, for whoever picks this up: Prometheus is *metrics*, not logs — the log counterpart in "the Grafana stack" is **Loki**, a separate Grafana Labs project; conflating the two is a common mix-up. **Tempo** (already named in this file's layout bullet as planned infra) is the real, automatic version of the `correlation_id`/`causation_id` design above — a proper tracing backend generates and propagates span/trace ids for you, replacing the hand-rolled MDC approach, but adopting it is a separate, later step, not a prerequisite for the MDC work above.

Structured logging itself is small and additive, not a rewrite of any logging call site — only the output *encoder* changes. **Verified 2026-09-27** (checked directly in the resolved jar, not assumed carried over from where this Boot feature originated around 3.4): Spring Boot 4.1.1 already ships `org.springframework.boot.logging.structured` with three built-in formats — `logging.structured.format.console=ecs|gelf|logstash` — no new dependency needed. MDC context (including `correlationId` once that filter exists) is folded into the output automatically via `ContextPairs`/`StructuredLoggingJsonMembersCustomizer`. Do this *after* the correlation id filter, not before — flipping the format has nothing interesting to show until MDC actually holds something. Which of the three formats barely matters yet, since nothing consumes them today.

Getting real day-to-day value (searching one correlation id across every service's logs in one place) is a separate, bigger step from just turning on JSON output: today `docker compose logs` only covers infra containers (Postgres, Keycloak, Kafka) — every application service still runs locally via `spring-boot:run`, not inside docker-compose, so there's nowhere for multiple services' logs to even converge yet, structured or not. That needs containerizing the app services plus Loki (+ a shipper like Promtail) alongside Grafana — additive infra, not an application rewrite, but its own later milestone alongside this file's existing Prometheus/Grafana/Tempo plans.

## Testing strategy (Layer 1 started in user-service — the plan for closing the rest)

Manual testing (see user-service status above) proves the design works once, for the paths a human thought to try — it doesn't run again on the next change, and can't cover concurrent requests or partial failures. Layer tests so most never need the full `docker-compose` stack — only a handful of true cross-service journeys do.

- **Layer 1 — unit tests** (no I/O, no Spring context, milliseconds each). Pure logic and Mockito-mocked repositories: `UserNotFoundException` thrown on the right conditions; `GlobalExceptionHandler` methods called directly with a constructed exception, asserting the `ProblemDetail`. Nothing here touches a database or a broker.
- **Layer 2 — repository/persistence integration tests** (`@DataJpaTest` + Testcontainers Postgres, one service's own DB only). A real, throwaway Postgres container per run, Flyway migrations applied against it exactly like production (this doubles as a migration-correctness check). Tests: repository query methods; `V5`'s CHECK constraints (`chk_users_status`, `chk_users_email`, `chk_users_deleted_consistency`) actually rejecting bad values via a raw insert; `uq_users_email` allowing a `DELETED` row's email to be reused; `V6`'s trigger bumping `updated_at` on both Hibernate and native updates. (The `alert_rules` `ON DELETE CASCADE` example this bullet used to cite no longer applies — that table is dropped as of `V5`; re-add an equivalent case once it's redesigned.) No other service needed. **Scaffolding exists (user-service):** `testsupport/PostgresTestContainerConfig` (a `@TestConfiguration` with a `@ServiceConnection` `PostgreSQLContainer` on `postgres:16-alpine`, shared across test classes via Spring's context cache) plus a placeholder `repository/UserRepositoryPostgresTest` (`@DataJpaTest`, `replace = NONE`, `@Import` of the config) that only proves container start → Flyway V1–V6 → Hibernate `validate`. Needs Docker running locally; no `.env`/exported variables needed since the container overrides `spring.datasource.*`. Note `@DataJpaTest` wraps each test in a rolled-back transaction — concurrency/race tests need committed data across threads, so they must opt out (`@Transactional(propagation = NOT_SUPPORTED)`) and clean up after themselves.
- **Layer 3 — service-layer integration tests** (`@SpringBootTest` + Testcontainers Postgres + `@EmbeddedKafka` where Kafka is involved). `spring-boot-starter-kafka-test`/`-webmvc-test`/`-data-jpa-test` are already dependencies in these `pom.xml` files, unused — this is what they're for. Tests: `UserService.createUser` persists both the `User` row and its `OutboxEvent` row in one transaction; `deleteUser` cascades and writes `UserDeletedPayload`; `OutboxRelay` against an embedded broker — correct headers, `published_at` only set after a confirmed send, the batch stopping on the first failed send rather than reordering. Still only one service's own containers — `@EmbeddedKafka` needs no other service running to test a producer's own output, or a future consumer's own reaction to a hand-crafted message on the topic.
- **Layer 4 — cross-service / end-to-end tests** (the real `docker-compose` stack, kept deliberately small). The only layer that actually needs multiple services running together — reserved for a handful of true journeys (e.g. create a user, create their device, delete the user, confirm the device is gone once device-service has a consumer), not exhaustive coverage. Slower and more fragile by nature; most coverage should live in Layers 1–3, this layer only confirms the wiring.

**Build order given 0% today:** start with user-service (it just reached a stable point) — Layers 1–2 first, then Layer 3 for the outbox/relay. Build device-service's upcoming `UserDeleted` consumer *with* tests from day one rather than retrofitting them later. Backfill the other services opportunistically, prioritizing whatever has already stopped changing (don't sink effort into deeply testing `EnergyUsageEvent.consumedEnergy` right before the cumulative-counter rename lands). Add the Layer 4 suite last, once there's a second service to actually react to something.

**CI (`.github/workflows/ci.yml`, started).** One job today, not yet the per-service matrix described below: `./mvnw test` against the whole reactor on `ubuntu-latest`, excluding every `*ApplicationTests` class (`-Dtest='!**/*ApplicationTests'`). Those are full `@SpringBootTest` context-load smoke tests - user-service's needs a live Postgres for Flyway and a reachable Keycloak issuer for the JWT decoder, neither of which exists in this job - so today's run covers Layer 1 unit tests (e.g. `UserServiceTest`) plus the Layer 2 Testcontainers test (`UserRepositoryPostgresTest`), which runs automatically because `ubuntu-latest` already has Docker and the filter above only excludes `*ApplicationTests`. Target, once more of Layers 1-3 exist: a matrix job per service (`user-service`/`device-service`/`ingestion-service`/`usage-service`, matching the no-parent-POM structure) — GitHub-hosted runners already have Docker running, so Testcontainers-backed tests (Layer 2/3) need no extra CI setup and could also bring the `*ApplicationTests` classes back once they're pointed at Testcontainers instead of `localhost`. A separate, less-frequent job (e.g. only on `main`) runs `docker compose -f infra/docker-compose.yml up -d` for the Layer 4 suite — `user-service` now has `/actuator/health` (only `health` exposed over HTTP, `permitAll` in `SecurityConfig`; other services don't have it yet) which would make "wait until services are ready" reliable there instead of ad hoc port polling - once user-service itself is actually a docker-compose service to depend on, which it isn't yet (today's `infra/docker-compose.yml` only has infra: the two Postgres instances, Keycloak, Kafka, InfluxDB - every application service still runs locally via `spring-boot:run`).

## Roadmap (planned / in progress — keep this current)

- **Cross-service contract for `user-domain-events` consumers (device-service, usage-service, alerting-service — none built yet).** *(Naming below predates the design docs: `docs/design/` uses topic `user.events.v1`, Kafka headers `event_id`/`event_type`/`schema_version`, and the deletion event is `UserDeletionRequested` — see "Outbox and account-deletion saga: decisions" under user-service status. Final topic/header names are not confirmed yet.)* Delivery is at-least-once, so every consumer must be idempotent (`DELETE WHERE user_id = ?` is) — this, not any cross-service cascade, is how a deleted user's devices are meant to get cleaned up. Each consumer needs its **own** `spring.kafka.consumer.group-id` matching its own service name (same pattern usage-service already uses for `energy-usage-events`) — Kafka fans a topic out per consumer *group*, not per partition, so a single partition doesn't limit how many independent groups can each read every message, but two services sharing one `group.id` would silently split messages between them instead of both receiving everything. Each consumer also filters by the `event-type`/`aggregate-type` headers since the shared topic carries every event kind, not just the ones it cares about.
- **Reading model — cumulative counter, not per-tick delta (decided, not yet implemented).** Real smart meters / IoT energy monitors report a monotonically increasing energy register (like an odometer), not "energy used this instant" — utility billing itself works by subtracting two register readings. `EnergyUsageDto` (ingestion-service) and both independent `EnergyUsageEvent` copies will change `consumedEnergy` → **`cumulativeEnergyKwh`** (validated `@PositiveOrZero`, not `@Positive`); the InfluxDB point field renames `consumed_energy` → `cumulative_energy_kwh`. `ContinuousDataSimulator` needs to change from a stateless per-tick random delta to **per-device running state** (a running total incremented each tick). Bonus this buys: the pipeline becomes self-healing against a lost/DLQ'd message — the next successful reading already reflects everything consumed since the last one, unlike the old delta model where a lost message loses that interval's energy forever. **Known problem, deliberately deferred:** a device reboot resets its counter to 0, which a naive subtraction reads as a large negative delta — needs detection before this is relied on; revisit later.
- **usage-service scheduled alert evaluation (query design for the cumulative model).** A fixed-cadence `@Scheduled` job. Per-user usage over a rule's `evaluation_window` = (last known cumulative reading **as of `now`**) − (last known cumulative reading **as of `now − window`**), each an "as-of" query summed per device then grouped by `user_id` — standard SQL via `ROW_NUMBER() OVER (PARTITION BY device_id ORDER BY time DESC)` filtered to `time <= boundary`, not a special interpolate/gap-fill feature (whether InfluxDB 3 Core exposes one is unverified — don't assume it without checking the actual version's docs). The `now` boundary is shared by every window, so it's computed **once per tick**, not once per window: ≈1 + (distinct windows in use, ≤5) queries per tick, still flat in user count. A **max-staleness cap** (a usage-service app property, not a per-rule column — a data-quality setting, not a user preference) rejects an as-of reading too old to trust rather than silently using a stale number; open decision whether that excludes just the stale device from the sum or skips the whole rule that cycle. True linear interpolation between straddling readings is optional future polish on top of this, not required for v1.
- **usage-service caches for the above.** (1) snapshot of enabled alert rules from whichever service ends up owning them (alert rules moved out of user-service entirely — see "user-service — status" — into their own, not-yet-built service; poll like `DeviceIdCache`, or event-driven); (2) device→user mapping — expand `DeviceIdCache` from an id set to `Map<userId, Set<deviceId>>`, and write `user_id` as an InfluxDB tag at ingest so the `GROUP BY user_id` works; (3) per-rule firing / edge-trigger state (under→over transition, last-fired) held locally in usage-service, **not** in whatever table replaces `alert_rules`.
- **alerting-service (new service).** Consumes `ThresholdExceededEvent` and delivers notifications.
- **Keycloak — started (2026-09-15); api-gateway itself still not built.** Keycloak runs locally (`infra/docker-compose.yml` + `infra/keycloak/realm-energy.json`, realm `energy-tracker`) and user-service validates JWTs against it (see "Identity (Keycloak)" above) — but there's no gateway yet, so `local-dev` (the realm's test client) is standing in for it. `users.id` *is* the Keycloak subject now (`V5`) — no separate `keycloak_id` column reconciling it against a app-generated id, unlike what an earlier version of this roadmap entry once sketched; there's no app-generated id left to reconcile against. Still ahead: api-gateway itself; moving `userId` from a path variable to token identity in every controller *that gets built* (none exist yet on the new schema — see "user-service — status"); per-request ownership checks (`findByIdAndUserId`-shaped) once there's a resource to own; audience (`aud`) claim validation once multiple services need to trust different audiences from the same realm (see "Identity (Keycloak)"'s known gap).
