## What this is

`home-energy-tracker` is a learning project: event-driven Spring Boot microservices tracking home energy consumption from IoT devices. Java 21, Spring Boot 4.1.1 (Spring Framework 7), Jackson 3, JUnit 5, Lombok, Maven multi-module; PostgreSQL, Kafka (KRaft), InfluxDB 3 Core, Keycloak.

**Target architecture: `docs/design/00-energy-tracker-blueprint.md`** (the "blueprint"; a **local-only** file — deliberately not committed, ignored via `.git/info/exclude`, so it exists on the user's machine only; it supersedes `01-outbox-design.md` and `02-processed-events-design.md`, which it grew out of). Eight services, database per service, transactional outbox + `processed_events`, an account-deletion saga by choreography, device tokens + a compacted registry topic for ingestion, cumulative meter readings in InfluxDB, tumbling-window alerts, a notification queue, AI over read-only tools, Spring Cloud Gateway. Build toward it, section by section (`§2.1` = user-service, etc.). Don't copy blueprint detail into this file — point at its sections. **Before implementing anything the blueprint specifies, check "Deviations from the blueprint" below**: some differences are deliberate, some are still open decisions for the user.

**Work order (user's plan):** finish user-service against §2.1 with real test coverage (§10), then rebuild device-service (§2.2), then the rest. device-, ingestion- and usage-service in the repo today predate the blueprint and will be rebuilt, not patched — don't invest in their current code.

**Design principle: model real IoT energy devices as accurately as reasonable** rather than a convenient simplification (e.g. the cumulative meter counter, blueprint D3).

## Layout

One Maven reactor: root `pom.xml` (packaging `pom`, parented on `spring-boot-starter-parent` 4.1.1) aggregates every module and holds the only Maven wrapper. Each module's `pom.xml` is parented on the root (`<relativePath>../../pom.xml</relativePath>`) and lists dependencies without versions. Root `<dependencyManagement>` imports the Spring Cloud, Spring AI, Resilience4j (2.4.0) and Testcontainers (2.0.5) BOMs and manages `contracts` at `${project.version}`.

- `contracts/` — plain jar (Lombok compile-only, no Spring): `EventEnvelope<T>`, `EventHeaders` (`event_id`, `event_type`, `schema_version`), and `user/`: `UserEvents` (topic `user.events.v1`, aggregate type `User`, producer `user-service`), `UserEventType`, `UserRegisteredData`, `UserUpdatedData`, `UserDeletionScheduledData`, `UserDeletionCancelledData`, `UserDeletionStartedData`, `UserDeletionFinalizedData` (each with a `SCHEMA_VERSION` constant), and `src/main/resources/events/<EventType>.v<N>.json`, the contract fixtures (one example envelope per event type and schema version). Used by user-service. See "Kafka event contract".
- `services/<name>/` — one module per service.
- `infra/` — `docker-compose.yml`, `.env.example`, `.env` (gitignored), `keycloak/realm-energy.json` (+ `README.md`, the realm's documentation; `user-profile.json`, the readable source of the profile embedded in the realm, and `embed-user-profile.ps1`, which copies it in), `kafka/kafka-topics.sh`. All container config lives here.
- `e2e/` — Layer 4 suite (Testcontainers `ComposeContainer`); stub, zero tests; only in the reactor under `-Pe2e`.
- `docs/design/` — the blueprint (00, local-only, never commit it), its two committed predecessors (01, 02), and `03-account-deletion-saga.md` (committed: the saga's full design write-up, without the roadmap).
- `scripts/get-token.ps1 -Role user|admin` — prints a Keycloak access token for the seeded test/admin user.

## Commands

### Infrastructure (from `infra/`)
```bash
docker compose up -d                         # user-db, keycloak-db, keycloak, mailpit (http://localhost:8025)
docker compose --profile kafka up -d         # + kafka broker, kafka-topics-init (one-shot, exits 0), kafka-ui (:8070)
docker compose --profile influxdb up -d      # + influxdb (legacy usage-service)
docker compose --profile kafka down -v       # --profile goes BEFORE the subcommand; without it the kafka containers are left running
```
`.env` is read only by docker compose (it must also define `USER_SERVICE_ADMIN_CLIENT_SECRET`: Keycloak fills the `user-service-admin` client's secret from it while importing the realm; `.env.example` has the template). Running a service from the IDE/`mvnw` needs its `${...}` secrets exported in the shell — user-service needs `USER_DB_PASSWORD`. Keycloak's `KC_HOSTNAME` pins every token's `iss` to `http://localhost:8080`, so no hosts-file entry is needed.

### Build (root wrapper; `.\mvnw.cmd` in PowerShell)
```bash
./mvnw test                                                      # unit tests (*Test) only, every module - no Docker needed
./mvnw verify                                                    # + integration tests (*IT, Testcontainers) via Failsafe - needs Docker
./mvnw -pl services/user-service -am test                        # one service (-am builds contracts first; without it contracts must be installed)
./mvnw -pl services/user-service -am test -Dtest=UserProfileServiceTest # one unit test class
./mvnw -pl services/user-service -am verify -Dit.test=UserSchemaIT -Dfailsafe.failIfNoSpecifiedTests=false -Dtest=NoUnitTests -Dsurefire.failIfNoSpecifiedTests=false  # one IT class only
./mvnw -pl services/user-service -am spring-boot:run             # run one service
./mvnw -pl services/user-service -am verify -Pcoverage           # JaCoCo coverage (unit + integration tests); report in services/user-service/target/site/jacoco/index.html
```

## Keycloak (local dev realm)

`infra/keycloak/realm-energy.json` is imported on first boot only into an **empty** Keycloak — editing it needs `docker compose down -v` before the next `up`. Realm `energy-tracker`; client `energy-cli` (confidential, direct-grant enabled, secret `secret` committed on purpose — throwaway dev credential, stand-in for the future gateway clients; renamed from `local-dev` on 2026-10-17) with an audience mapper adding `user-service` to `aud`; realm roles `user`, `admin` (the `default-roles-energy-tracker` composite grants `user`); seeded `testuser@example.com`/`Testpassword1` (id `11111111-…`, role `user`) and `admin@example.com`/`Adminpassword1` (id `22222222-…`, role `admin` only: it is deliberately not given the default-roles composite, so it does not hold `user`). Fixed ids are for this local realm only — blueprint §1.3.4 forbids deterministic ids in any real realm. Keycloak runs on its default port 8080; `KC_HOSTNAME` only fixes the advertised issuer (`http://localhost:8080`), not where it is reachable: a container on the compose network calls it as `http://keycloak:8080`, and a containerised service overrides only `jwk-set-uri`, never `issuer-uri` (a string that is compared, not fetched). Only the client name follows the blueprint's naming; the rest deliberately stays — see "Names" under Decided. Since 2026-10-18 the realm also locks the user profile (`edit: [admin]` on email, username and names; see the saga section), requires email verification (registration asks for the email only, then a verification mail, then the user chooses a password), allows password reset, sends its mail to Mailpit (`mailpit:1025`, UI at http://localhost:8025), records events and admin events, and has the service-account client `user-service-admin` (`manage-users`, `view-users` only) whose secret is the placeholder `${USER_SERVICE_ADMIN_CLIENT_SECRET}`, filled from the environment while importing. The realm JSON cannot hold comments (Keycloak does not parse `//` comments, nor `"//key"` pseudo-comment keys), so every note on a setting lives in `infra/keycloak/README.md` (every setting explained, the registration endpoint, the event and mail model, the service account), which must be kept in step with the file; `RealmFileTest` fails on a `"//"` key. The user-profile configuration is one escaped line inside the realm (JSON strings cannot span lines; Keycloak reads only the first array element), so edit `user-profile.json`, run `powershell -File infra/keycloak/embed-user-profile.ps1` and commit both (`RealmFileTest` fails when they differ). `energy-cli` has `rootUrl`/`baseUrl` `http://localhost:3000`, which gives Keycloak's "Account updated" page (a mailed link finished on another device) a "Back to Application" link; flows that continue in the browser that started them redirect to the application by themselves.

## Kafka event contract

- **User/device events (`user.events.v1`, later `device.events.v1`, …) use the shared `contracts` module.** The value is the JSON-serialized `EventEnvelope<T>` (blueprint §3.4) — no Java class names, no `__TypeId__`. `eventType`/`aggregateType` are `String`s in the envelope so consumers survive new types; producers use the `UserEventType` enum's `value()`. Consumers read the envelope with `data` as a tree, dispatch on `eventType` (also in the `event_type` header), then convert `data`; unknown fields are ignored (Jackson 3 default); unknown `schemaVersion` → DLT. Key = `aggregateId` (text; `StringSerializer`, never `UUIDSerializer`).
- **Consumers** (blueprint §3.3): one consumer group per service named after it; record-level ack after the side effect; `processed_events (event_id, handler)` inserted in the same transaction; poison/deserialization errors → `<topic>.dlt` via `ErrorHandlingDeserializer` + `DeadLetterPublishingRecoverer`; `DataAccessException`s retry indefinitely (never DLT — skipping breaks ordering); `concurrency ≤ partitions`, no `@Async` in listeners.
- **Topics are created by `infra/kafka/kafka-topics.sh`** (run by the `kafka-topics-init` compose service, `--if-not-exists`, broker auto-create off): `user.events.v1` 3 partitions, RF 1 (one broker). Every blueprint topic (§3.5) and its DLT goes in this script, never a `NewTopic` bean. Partition counts are permanent once a broker has real data (§17.9). Use dots only in topic names (Kafka warns that `.`/`_` collide in metric names).
- Legacy exception: `energy-usage-events` (legacy ingestion → usage) still uses per-service `NewTopic` beans and per-side event copies with `spring.json.type.mapping`; it disappears when those services are rebuilt onto `energy.readings.v1`.

## Conventions

- **Comments.** Learning project — heavy explanatory comments are intentional; don't strip them as cleanup. (The user sometimes deletes comment blocks on purpose after saving them elsewhere; don't flag that.) Never write "see CLAUDE.md" pointers in code — explain inline.
- **Schema.** Flyway owns all DDL; `ddl-auto=validate`; changes are new forward migrations, never edits to an applied `V` file. Names: `pk_/uq_/chk_/idx_<table>_…`; `CURRENT_TIMESTAMP` over `now()`. user-service lets **the database own time**: `created_at` default + a `BEFORE UPDATE` trigger stamping `updated_at` (V6), mapped `@Generated` (`insertable/updatable = false`); the trigger leaves `version` alone, so native `UPDATE`s bump `version = version + 1` themselves. Other services adopt the same when rebuilt.
- **State transitions** are compare-and-set: every status-changing `UPDATE` carries `WHERE status = '<expected>'` and reports rows affected (`int`). The database constraint (PK, partial unique index) is the real uniqueness guarantee; any app pre-check only improves the error message.
- **Packages.** A service is organised by feature, not by layer (user-service since 2026-10-26; the other services adopt it when they are rebuilt): a feature's controller, service, DTOs, entity, repository, exceptions and jobs sit in one package named after it, so there is no `controller`, `service`, `dto`, `entity`, `model`, `util` or `common` package to scatter a feature across. A class is named for what it does (`UserProfileService`, not `UserService`), and a controller serves one feature's routes. Tests mirror the main packages (a class's test sits in its package, so package-private members stay reachable), and a test that exercises a feature end to end sits with that feature, not with the layer it passes through (a deletion flow test is in `deletion/`, not `security/`). Shared test helpers live in `testsupport/<kind>/` (`containers`, `keycloak`, `jwt`, `data`). Do the moves with `git mv` and as their own commit, so `git log --follow` keeps working.
- **Entities.** Lombok `@Data @Builder @NoArgsConstructor @AllArgsConstructor`; fields with defaults need `@Builder.Default`; exclude lazy associations from `equals/hashCode/toString`.
- **Outbox writer rules.** `OutboxService.record*` methods are `@Transactional(propagation = MANDATORY)` (must join the business transaction). Only the request that actually changed the row emits (check the native query's row count, or the entity's version before/after `saveAndFlush`). Build the event from the row as the database now holds it (re-read after a native update); `occurredAt` = the row's DB-stamped `created_at`/`updated_at`/`deletion_requested_at`/`deletion_started_at`/`deleted_at`. The event id is generated once, in the envelope, and the outbox columns are derived from that same envelope. `aggregate_version` has gaps (bumps that emit nothing) — consumers compare with `>`, never `previous + 1`.
- **Never call a `@Transactional`/`@Scheduled`/aspect-advised method via `this.`** — self-invocation bypasses Spring's proxy silently. (It happened once: an old relay self-called its own `markPublished`, so `published_at` was never persisted.) Put the method on another bean.
- **Web.** One `@RestControllerAdvice GlobalExceptionHandler` per service returning `ProblemDetail`; user-service's is the reference (extends `ResponseEntityExceptionHandler`; `type` under `https://home-energy-tracker/problems/`, `title`, `status`, `detail`, `instance`, `timestamp` on every error, same as the security 401/403 handlers; `OptimisticLockingFailureException` → 409; `DataIntegrityViolationException` → 409 only for a unique violation (SQLState 23505 in the cause chain), any other integrity violation → logged 500; catch-all 500 logs the cause and rethrows `AccessDeniedException`/`AuthenticationException`). DTOs are records with `@Builder` and `@JsonPropertyOrder` (Jackson 3 orders alphabetically and matches names verbatim, camelCase). Bean Validation on request DTOs + `@Valid`. User identity comes only from the JWT `sub`; ownership is `WHERE user_id = :sub` in the query and a miss is 404, never 403 (§7.5).
- **Config.** `@Value` into `@Bean` methods or constructor parameters (not onto a `final` field with `@RequiredArgsConstructor` — see gotchas). Secrets only from env vars. `application.yaml` (spaces only — YAML forbids tabs).
- **Logging.** Blueprint §14.1: never log tokens, secrets, emails or request bodies; log ids. (The old `LoggingAspect`/`ExecutionTimeAspect`/`@SkipLogging` were removed 2026-09-28 — they logged arguments and return values, including emails. `spring-boot-starter-aspectj` stays in the pom for Resilience4j's annotations.) Logging/metrics/tracing come from Micrometer + structured logging (step 6).
- **Git.** The user usually commits; only commit when told. Commit messages: meaningful title + "-" bullet description; no `Co-Authored-By` line and no `Claude-Session` trailer (the user writes neither). Never read, print or verify `infra/.env` in any way (docker compose reading it internally is fine).

## Framework and tooling gotchas (verified in this repo)

- Boot 4 starter renames: `spring-boot-starter-security-oauth2-resource-server`; `spring-boot-starter-aspectj` (Boot 4 no longer manages `spring-boot-starter-aop`); `@DataJpaTest` lives in `spring-boot-starter-data-jpa-test`.
- Testcontainers 2.x: modules are `testcontainers-postgresql`, `testcontainers-junit-jupiter`, …; `org.testcontainers.postgresql.PostgreSQLContainer`; `@ServiceConnection` overrides `spring.datasource.*`.
- Jackson 3: `tools.jackson.databind.*` (annotations still `com.fasterxml.jackson.annotation`); unknown properties ignored by default; `writeValueAsString` throws unchecked.
- Spring 7: `ProblemDetail.getType()` may be null (Spring 6 defaulted to `about:blank`); trailing-slash URLs no longer match; `@Min/@Max` on `@RequestParam` validates natively (`HandlerMethodValidationException`). Standalone MockMvc needs `AuthenticationPrincipalArgumentResolver` for `@AuthenticationPrincipal`. `PageImpl` silently corrects inconsistent totals; an unpaged page reports size = content size.
- Hibernate: a native `@Modifying` query bypasses the persistence context — an entity loaded earlier in the same transaction stays stale; use `clearAutomatically = true` (detaches everything) then re-read. Hibernate auto-flushes pending changes before native queries; `JdbcTemplate` does not (flush first). `saveAndFlush` of an unchanged entity — or a setter with the same value — issues no `UPDATE` and no version bump. In `@DataJpaTest` (one transaction per test): flush before JDBC reads, clear before entity re-reads.
- Lombok: `@Value` on a `final` field + `@RequiredArgsConstructor` → Spring looks for a bean of type `int` (Lombok doesn't copy the annotation to the constructor parameter).
- PostgreSQL: row locks are held until commit/rollback, and a blocked `UPDATE` re-evaluates its `WHERE` against the committed row (READ COMMITTED) — the basis of every CAS here. `pg_try_advisory_xact_lock(key)` is non-blocking, released at transaction end, scoped per database, not tied to any table; callable as a Spring Data native query returning `boolean`. `CURRENT_TIMESTAMP` is the transaction start time (tests that insert then update in one transaction must seed old timestamps). Unquoted identifiers fold to lowercase. pgjdbc 42.7 and `JdbcTemplate` cannot bind a `java.time.Instant` parameter (both handle `OffsetDateTime`, the JDBC 4.2 type for `timestamptz`); reading one back as `Instant.class` works.
- Spring Boot 4.1.1 ships structured logging (`logging.structured.format.console=ecs|gelf|logstash`, MDC included). `resilience4j-spring-boot3:2.4.0` compiles against Boot 4.1.1 with `spring-boot-starter-aspectj` (runtime interception not yet verified). A flat dotted key under `logging.level` works in YAML.
- Spring Kafka's default dead-letter topic is `<topic>-dlt` (checked against spring-kafka source, per legacy usage-service's `KafkaTopicConfig`); the blueprint names them `<topic>.dlt`, so consumers need a custom destination resolver.
- `apache/kafka:4.3.1`: CLI at `/opt/kafka/bin/`, entrypoint ends in `exec "$@"` (override `command` only), runs as `appuser`.
- `micrometer-core` (`Gauge`, `MeterBinder`, `MeterRegistry`) is not declared in user-service's pom: it arrives through `spring-boot-starter-actuator` → `spring-boot-starter-micrometer-metrics` → `spring-boot-micrometer-metrics` → `micrometer-core` (Boot 4). (`resilience4j-circuitbreaker` was dropped from user-service's pom with the relay's circuit breaker; step 5 adds it back for the Keycloak admin client, whose version is still managed by the root BOM.)
- Keycloak import: `${NAME}` in the realm file is replaced by the environment variable `NAME`, and a placeholder with no such variable is left as it is (that is why the theme placeholders like `${username}` survive and why an unset secret variable becomes the literal placeholder text). The user-profile configuration is imported from the realm's `components` as one JSON document escaped into a string. Keycloak marks its cookies `Secure` even on `http://localhost`, so a Java test that plays a browser has to handle cookies by hand (`KeycloakBrowser`).
- A Turkish default locale (the developer's machine) makes `String.toUpperCase()` turn `i` into a dotted `İ`: use `Locale.ROOT` in tests that build addresses or compare case.
- Git Bash on Windows: prefix `docker exec/run` with `MSYS_NO_PATHCONV=1` when passing absolute container paths.

### Implemented
- **Schema**: V1–V4 are history; V5 resets around `users.id = sub` (UUID, never generated), `status ACTIVE/DELETING/DELETED`, `deletion_requested_at`, `deleted_at`, `devices_deleted`, `keycloak_disabled_at`, `version`, `chk_users_status`, `chk_users_email`, `chk_users_deleted_consistency`, partial `uq_users_email` (lower(email), non-DELETED), `idx_users_deleting`; V6 `updated_at` trigger; V7 `outbox_events` (§3.1 shape; payload NOT NULL and must be a JSON object); V8 `outbox_events.parked` (`chk_outbox_events_parked_unpublished`), payload < 256 KB, pending index `WHERE published_at IS NULL AND NOT parked`, `idx_outbox_events_parked`; V9 `users.keycloak_deleted_at`, `chk_users_deleting_consistency`, `chk_users_keycloak_disabled_not_active`, `chk_users_keycloak_deleted_only_deleted`; V10 `processed_events` (§3.3; no consumer uses it yet). Each column is explained in the migration comments. V11-V14 (saga step 5b, 2026-10-24; one concern per file): V11 `users_add_deletion_schedule_and_scheduled_status` (`deletion_scheduled_for`, `deletion_started_at`, a backfill that gives DELETING and DELETED rows both the value of `deletion_requested_at`, the status check with `DELETION_SCHEDULED`, `chk_users_deletion_scheduled_consistency`, `chk_users_deletion_started_consistency`, `chk_users_deletion_scheduled_after_requested`, the partial index `idx_users_deletion_scheduled`, `idx_users_deleting` moved to `deletion_started_at`), V12 `users_allow_keycloak_deleted_at_while_deleting` (`chk_users_keycloak_deleted_only_deleting_or_deleted`), V13 `create_user_deletion_participants_table` (primary key `(user_id, participant)`, FK to `users`, name format check, `acked_at` and `waived_at` never both, partial index on pending rows), V14 `users_drop_keycloak_disabled_at_and_devices_deleted`. The entity maps the new columns and no longer the dropped ones.
- **Provisioning** (`UserProvisioningService.ensureUsable`, run by `UserProvisioningInterceptor` before every `/api/v1/users/**` controller, and only for a token holding `ROLE_user`: the interceptor runs before method security, so it checks the role itself instead of relying on the URL rule having rejected other roles): `insertIgnoringConflict` (`ON CONFLICT (id) DO NOTHING`, R8) → re-read → `UserRegistered` only from the winning insert; display name from `name` → `given_name` → `preferred_username` local part; the token's email is read only to create the row and never written afterwards: a verified token email that differs from the row (case ignored: Keycloak lower-cases, the unique index agrees) is counted in `user.email.token.mismatch` (no tags, never logged), nothing else happens; a DELETING or DELETED user gets 410 `AccountDeletedException` (problem type `account-deleted`; `UserStatus.isGone()`), while ACTIVE and DELETION_SCHEDULED pass (a scheduled account can still be read and cancelled).

### Relay: known gaps, deferred on purpose (2026-10-03)
The relay design is settled (see "Relay failure policy" under Decided). These came out of reviewing it and are not worth doing yet; pick them up with the step named, or when a load test or an incident asks for them.
- **Abandoned producer records become duplicates (mostly fixed 2026-10-04).** A tick that hits its deadline used to leave its records in the producer for `delivery.timeout.ms` (120 s), adding a copy per failing tick. Now `delivery.timeout.ms` 5000 / `request.timeout.ms` 3000 end them at about the same moment as the tick; a few duplicates around an outage are still possible and consumers absorb them (`processed_events`, version guards). Measured in `RelayIT`: after a broker pause the relay's own deadline (`java.util.concurrent.TimeoutException`) fires before the producer's expiry, and from the second failed tick on the producer has lost its metadata, so `send()` throws after one `max.block.ms` (5 s) wait.
- **Cold producer, broker down: one `max.block.ms` wait per tick (verified 2026-10-04 with a probe against kafka-clients 4.2.1 / spring-kafka 4.1.1).** A metadata timeout makes `send()` *throw* (`KafkaException("Send failed")` wrapping `TimeoutException`), and the phase 1 loop breaks on the first throw, so a tick costs one `max.block.ms` (1.5 s since 2026-10-04, was 5 s), not 50 of them. A *warm* producer (metadata cached) accepts the sends and the tick ends on its own 5 s deadline instead. Confirm both timings in `RelayIT`.
- **Spring wraps every producer error** (`KafkaProducerException "Failed to send"` in the future, `KafkaException "Send failed"` when `send()` throws); `OutboxBatchPublisher.rootCause` strips those wrappers so `last_error`, the log and the breaker see the real exception (fixed 2026-10-04).
- **No database timeouts.** Without `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`, the JDBC `socketTimeout` and `tcpKeepAlive`, a hung session can hold the advisory lock (every other instance then gets `IDLE` forever, silently) and a hung JDBC call blocks the single scheduler thread. Step 6.
- **Scheduler pool size is 4** (`spring.task.scheduling.pool.size`, raised from Boot's default of 1 on 2026-10-17): a failing relay tick (5–10 s) no longer delays the purge job, the promoter (3rd task, step 5e) or, from 5f and 5g, the finaliser and the Keycloak job (raise the size when those arrive); a `fixedDelay` task still never overlaps itself. If virtual threads are enabled in step 6, Boot builds a different scheduler and ignores this property (`spring.task.scheduling.simple.concurrency-limit` applies instead).
- **Topic validation.** `outbox_events.topic` has no format check, and a wrong or missing topic stalls the relay on that row forever (a missing topic shows up as metadata timeouts, which look transient). Fix: a check in a new migration (`^[A-Za-z0-9._-]{1,249}$`) and optionally a startup check that the topic exists.
- **Database failures are deliberately not counted as failed ticks** (they say nothing about Kafka, and a longer wait would only slow the recovery from a database blip). They fail loudly: the exception reaches Spring's scheduler, which logs it at ERROR and keeps the schedule. Optional: catch `DataAccessException`/`TransactionException` and log one WARN line without the stack trace.
- **Alerts.** The gauges exist but nothing scrapes them before step 6. Rules to add there: `outbox.oldest.pending.age.seconds` > 60 s for 2 min (warn) and > 300 s (critical), `outbox.parked.rows` > 0, `outbox.relay.consecutive.failed.ticks` > 0 for 2 min (warn). The age gauge reads `NaN` while the database is down.
- **Accepted trade-offs:** the transaction (and its advisory lock) stays open while the relay waits for the acks (5–10 s worst case; a session-level leader lock with short transactions would avoid it); each instance has its own backoff state and the backoff sits before the lock, so while the leader waits another instance may take the lock and attempt (the cluster-wide retry rate is N times the single-instance one - still a few records per ~30 s), and a failover starts with no backoff; one global `seq` order, so one unavailable partition would hold everyone's events (not possible with one broker).

### Decided (keep)
- **Contract fixtures live in `contracts/src/main/resources/events/`** (blueprint §10.3.5: `src/test/resources`), so any service's tests read them from the `contracts` jar without a test-jar. - **Provisioning on every `/api/v1/users/**` request** (blueprint: `GET /me` only). The token-to-row email sync that used to run was removed in saga step 5d: email is changed only through user-service, so a token's email is read only to provision (a divergence is counted, see saga item 8).

- **Admin read endpoints** (`GET /admin/users`, `/admin/users/{id}`) beyond the blueprint; keep them minimal (§17.2).
- **Relay send mode** (2026-09-29): pipelined batch + one wait, instead of the blueprint's per-record `.get(5 s)` (§3.2). Same guarantees for delivery (mark only after ack, mark only the acknowledged prefix, all inside the locked transaction), about one network round trip per batch instead of one per record. Weaker than the blueprint on ordering: "stop at the first failure" now stops *marking*, not *sending* - rows after a failed one are already with the producer and may reach the log before it, so a consumer can see an aggregate's newer event before its older one. The tail still converges (every delivered-but-unmarked row lies inside the next window, so it is resent after the failed row), which is why consumers must apply the version guard to state projections (blueprint §5.3 has no row for this case yet). Not `whenComplete` callbacks: they run on the producer's network thread after the transaction has committed and the advisory lock is gone.
- **Relay backoff instead of a circuit breaker** (2026-10-04; replaces the Resilience4j `relayProducer` breaker: window 5 / 100 % / 30 s open / half-open probe). The relay pulls from Postgres with one scheduler thread, so a dead Kafka cannot pile up threads, the outbox table is the buffer, and the producer already backs off its own reconnects and retries; what a failing tick wastes is the relay's own DB connection + advisory lock (up to `send-timeout-ms` per tick), an `attempts`/`last_error` UPDATE and a WARN, every ~7 s. A breaker also opened only after 5 such ticks (~35 s), counted partial progress as a failure, idled a fixed 30 s however short the outage, sent a full 50-record batch as its "probe", and its open-state gauge flapped to 0 during every probe (so a "= 1 for long" alert could never fire). The replacement is the consecutive-failed-tick backoff described under "Outbox + relay", plus `max.block.ms` 1500 so a failing tick ends sooner. A poison row at the head of the queue is throttled by the same mechanism (no classification of exceptions needed). Resilience4j stays in the plan for the Keycloak admin client (step 5), where a breaker fits: request/response with threads waiting.
- **Relay failure policy: stall and alert, never skip** (2026-10-02; replaces the blueprint's "park after 20 failed attempts" and this file's earlier "park permanent errors immediately" rule — both turn a delay into a loss: a parked `UserUpdated` with an email change leaves notification-service mailing the old address, because user-service's own row already holds the new email and the `GET /me` re-sync never fires again; a parked `UserDeletionRequested` leaves the user `DELETING` forever). An outbox event may arrive late, twice or slightly out of order, never not at all. Every send failure stops the batch at the failed row (earlier rows marked published, the failed row gets `attempts + 1` and `last_error`, later rows stay pending and are resent — duplicates are absorbed by the consumers' version guards and `processed_events`). A misconfiguration (topic ACL, ...) stalls delivery and alerts (`outbox_oldest_pending_age_seconds`); fixing it drains the backlog in order. Poison rows are prevented at write time instead (payload < 256 KB check, constant topic, `StringSerializer`). The `parked` column and the `NOT parked` filter stay for a manual operator quarantine added with the replay endpoint (step 7, together with `UserSnapshot` so consumers converge); nothing parks a row automatically.
- **Topic provisioning script** `infra/kafka/kafka-topics.sh` + `kafka-topics-init` = the blueprint's `kafka-init`. Kafka image `apache/kafka:4.3.1` (blueprint 3.9.0); Postgres 16 (blueprint 17 — bump with "Postgres topology" below).
- **`DELETING`/`DELETED` accounts get 410 everywhere** (2026-09-28; with the saga's `DELETION_SCHEDULED` state, 410 applies only from `DELETING` on, and a scheduled account is readable and gets 409 on writes). `AccountNotActiveException` was renamed `AccountDeletedException` (done 2026-10-09): 410, problem type `account-deleted`, for `DELETING` and `DELETED` on every endpoint including a repeated `DELETE /me` (blueprint answers 202 for a repeated `DELETE` on `DELETING` — the difference is cosmetic; the resulting state is the same, so `DELETE` stays idempotent). Keep `requestDeletion`'s `markDeleting == 0` branch: two parallel `DELETE`s can both pass the interceptor while `ACTIVE`; the loser returns quietly (202, no second event).

### Account-deletion saga (final design 2026-10-18; replaces the 2026-09-28 plan)
Blueprint §6.1 plus a cancellable grace period (the blueprint has no undo; deliberate deviation). The long-form write-up is `docs/design/03-account-deletion-saga.md`; keep both in step. The database change always commits first; every Keycloak call happens after a commit, is idempotent, and is retried by a job. Keycloak never learns our states.
1. **States**: `ACTIVE → DELETION_SCHEDULED → DELETING → DELETED`, and `DELETION_SCHEDULED → ACTIVE` on cancel. Every transition is a compare-and-set on `status`.
2. **Schema (V11-V14, done 2026-10-24)**: status check gains `DELETION_SCHEDULED`; columns `deletion_requested_at` (when the user asked; kept), `deletion_scheduled_for` (absolute, `CURRENT_TIMESTAMP + grace` computed in SQL, so a later config change moves no existing row), `deletion_started_at` (set by the promoter); `keycloak_disabled_at` and `devices_deleted` dropped (the first with its V9 check; completion tracking moves to `user_deletion_participants`, below); `keycloak_deleted_at` allowed on `DELETING` and `DELETED`; checks tie each timestamp to the statuses that imply it (`(status='ACTIVE') = (deletion_scheduled_for IS NULL)`, `(status IN ('DELETING','DELETED')) = (deletion_started_at IS NOT NULL)`, `deletion_scheduled_for >= deletion_requested_at`); partial indexes `idx_users_deletion_scheduled (deletion_scheduled_for) WHERE status='DELETION_SCHEDULED'` and `idx_users_deleting (deletion_started_at) WHERE status='DELETING'` replace the old one. Backfill first: a dev row already `DELETING` gets `deletion_scheduled_for` and `deletion_started_at` = its `deletion_requested_at`. `AdminUserResponse` loses `keycloakDisabledAt` and `devicesDeleted` (done) and gains the new columns (done) and the participants (5c). Table `user_deletion_participants (user_id → users, participant, acked_at, waived_at)`, primary key `(user_id, participant)`: one row per participant required for that deletion, written by the promoter in the same transaction as `DELETING`. The required set is fixed when cleanup starts, from `app.user.deletion.required-participants` (validated at startup against the participants that have an ack handler, so a typo fails the boot; empty until participant services exist), so a later config change never rewrites an in-flight deletion's completion contract. A participant retired for good is waived by an explicit versioned migration (`waived_at` set, so audit tells waivers from real acks); a participant added later affects only deletions that start afterwards (an in-flight row can be given its row by a migration plus a re-emitted `Started`).
3. **HTTP**: `DELETE /users/me` → CAS `ACTIVE → DELETION_SCHEDULED` + `UserDeletionScheduled` → 202; repeated while scheduled → 202 with the same date and no event (decided; not 409). `POST /users/me/deletion/cancel` → 204; CAS `DELETION_SCHEDULED → ACTIVE` with `deletion_scheduled_for > CURRENT_TIMESTAMP` (clears the three deletion columns) + `UserDeletionCancelled`; already `ACTIVE` → 204 no-op; overdue but not yet promoted → 409 `deletion-deadline-passed`; `DELETING`/`DELETED` → 410. `GET /users/me` returns `status` and `deletionScheduledFor` (the frontend shows Cancel from them; the backend is the enforcement). `PATCH /users/me` while scheduled → 409 `deletion-scheduled`; `DELETING`/`DELETED` → 410 on every endpoint. Cancel and promote exclude each other through the row lock and the status CAS; the time comparison only decides who may start, so being late by one transaction is harmless.
4. **While `DELETION_SCHEDULED`**: login always works (Keycloak untouched); reads, device readings and AI questions keep working; sensitive writes are refused. Other services freeze their own writes (device claim first; alert rules are each service's call) from a per-user flag fed by `UserDeletionScheduled`/`UserDeletionCancelled` (version-guarded, tombstone-wins on `Started`), not from a central lock; `UserDeletionStarted` is the hard stop. Password and MFA changes stay allowed in Keycloak (a compromised account must be recoverable).
5. **Events** (`user.events.v1`, key = user id, each with a fixture): `UserDeletionScheduled` (data `deletionScheduledFor`; `occurredAt` = `deletion_requested_at`), `UserDeletionCancelled` (empty; `updated_at`), `UserDeletionStarted` (empty; `deletion_started_at`; renamed from `UserDeletionRequested`, whose fixture is deleted because no consumer or released topic ever depended on it), `UserDeletionFinalized` (empty; `deleted_at`). Consumers delete their data on `Started` and rerun on `Finalized`. Done in 5c: all four types, data records and fixtures exist; `Scheduled` and `Cancelled` are emitted by the HTTP endpoints, `Started` by the promoter (5e); `Finalized` waits for the finaliser (5g).
6. **Jobs** (`fixedDelay`, bounded batch, config under `app.user.deletion.*`; rows are claimed by a compare-and-set or `FOR UPDATE SKIP LOCKED`; dev values: grace 5 min, quiet period 1 min, intervals a few seconds):
   - **Promoter** (done, 5e): `DELETION_SCHEDULED AND deletion_scheduled_for <= CURRENT_TIMESTAMP` → one transaction **per account**: email `deleted+<id>@invalid`, display name `Deleted user`, `DELETING`, `deletion_started_at`, version+1, one `user_deletion_participants` row per required participant, outbox `UserDeletionStarted`. Needs no external call. The job lists the overdue ids with a plain read and the compare-and-set `UPDATE` of each account is its claim: it takes the row lock, so a cancel or a second promoter on the same account blocks until the other commits and then matches nothing (the design first said one `FOR UPDATE SKIP LOCKED` batch transaction; per-account transactions were chosen because one account that cannot be promoted would otherwise block the whole batch, forever, as it is always first in line; a failure is logged, counted and the loop moves on). Two promoters walking the same list serialise on the row locks instead of splitting it: harmless, and the duplicate work is bounded by the batch size.
   - **Keycloak hard delete**: `DELETING AND keycloak_deleted_at IS NULL` → admin API delete (404 = success) → `keycloak_deleted_at`. The tx stays open during the call; small batch and short timeouts bound it, and a duplicate delete by two instances is harmless.
   - **Finaliser**: `DELETING AND keycloak_deleted_at <= CURRENT_TIMESTAMP - quiet period AND` the user has no participant row with `acked_at IS NULL AND waived_at IS NULL` (10 min in production: access tokens live 5 min and no new one can be issued after the Keycloak delete) → `DELETED`, `deleted_at`, version+1, outbox `UserDeletionFinalized`.
   - **Ack consumers** (one event type per participant service on its owner's topic, starting with `UserDevicesDeleted` on `device.events.v1`; group `user-service`, `processed_events`, `.dlt`): `UPDATE user_deletion_participants SET acked_at = CURRENT_TIMESTAMP WHERE user_id = ? AND participant = ? AND acked_at IS NULL` (0 rows = not required for this deletion, or already acked: ignore); the `users` row is not touched, so no version bump or lock contention. An ack means "I deleted everything I hold for this user and reject new writes for them"; a service acks even when it found nothing. Types, data and fixtures go into `contracts`. While the required set is empty (no participant service exists yet) the saga completes by time alone. A required participant that never acks stalls finalisation and alerts (never forced); the watchdog names the missing participant. `UserDeletionStarted` does not carry the set: services react to it regardless of who else participates.
   - **Watchdog gauges** (like `OutboxMetrics`): scheduled count, oldest `DELETING` age, oldest pending Keycloak delete age, pending acks per participant, circuit state.
7. **Keycloak admin client**: a service-account client (`manage-users`, `view-users` only) with the secret from an env var; `RestClient` with connect 1 s / read 3 s timeouts; token cached until shortly before expiry; Resilience4j programmatic `CircuitBreaker` and `Retry` on idempotent calls only (no TimeLimiter on blocking calls). Keycloak down never fails a request: the row is already committed. Keycloak's own admin events are switched on as the audit trail for anything done in its console.
8. **No email sync** (decided 2026-10-18, done in step 5d: the sync method, its query and its tests are gone): with email edit admin-only in Keycloak, every supported change goes through user-service, so the token's `email` is only read to provision a new user (plus the `email_verified` check, unchanged). A token is a cache of Keycloak state up to 5 minutes old, and writing it back into the database would flip a freshly changed email back. Replaced by detection: a counter `user.email.token.mismatch` when a verified token email differs from the row (expect up to 5 minutes of noise after a legitimate change; never logged with the address). The Keycloak console is not used by the application's `admin` role (it holds no `realm-management` role; verified: 403 on Keycloak's admin REST) but by infra operators, so "don't edit users in the console" is a runbook backed by Keycloak admin events, not a technical control. An email that does diverge is repaired by an admin action (later).
9. **Orphan email collision**: a row that outlived its Keycloak user (deleted by hand) still holds its email in `uq_users_email`, so a new registration with that address cannot be provisioned. On that unique violation, ask Keycloak whether the old `sub` exists; if not, set the old row's `deletion_scheduled_for` to now (the promoter scrubs it) and answer the new user 503 with `Retry-After`. Never hand the address to the new `sub` directly.
10. **Keycloak realm (verified against 26.7.3 on 2026-10-18 with throwaway containers)**: the realm blocks email edits today only through `editUsernameAllowed: false` (Account API answers 204 and silently ignores the email; first/last name stay editable), and flipping that flag makes email editable. The robust lock is the user profile: `permissions.edit: ["admin"]` on `email`, `username`, `firstName`, `lastName` (Account API → 400; `kc_action=UPDATE_PROFILE` shows disabled fields and rejects a forced submit; registration still works with email + password; `kc_action=UPDATE_PASSWORD` still changes the password). The admin API still changes email under the lock (a body with only `email` also moves the username; the address is lower-cased; `emailVerified` is honoured); a duplicate answers 409 `User exists with same email` (case-insensitive; 25 parallel races between two users gave one 204 and one 409, never a 5xx); an old refresh token keeps working and the next access token carries the new `email`/`preferred_username`, while an access token issued earlier keeps the old email until it expires; a Keycloak action link goes to the user's current address and dies ("Invalid email address") once the email changes. `UPDATE_EMAIL` is disabled by default and, even enabled, completes without a form while email is admin-only, so Keycloak's verify-before-change cannot be combined with the lock. The Account Console stays (password, MFA); nobody hashes passwords in user-service. Step 5a (2026-10-18) put all of this into `realm-energy.json` and `docker-compose.yml`, covered by `KeycloakRealmIT`: the profile lock, `verifyEmail: true`, `resetPasswordAllowed: true`, SMTP to Mailpit, events with the `email` listener, admin events, the `user-service-admin` client. Verified on the way: with `verifyEmail` on, the registration form asks for the email only, Keycloak mails a verification link, and the user then sets a password (that first password also sends one "Update password" notice); this is Keycloak 26.7's design (the form shows the password fields again with `verifyEmail` off; a deprecated switch on the registration flow's Password Validation step restores them: tested by hand 2026-10-18 via the admin API after import - form with email + password + password again, one "Verify email" mail and no "Update password" mail, no token before verification (`invalid_grant`, "Account is not fully set up") - but not applied: deprecated, the account gets a password before the mailbox is proved, and a permanent switch needs the flow definitions in the realm or a setup call; documented as an alternative in `infra/keycloak/README.md`, and the sign-up "Update password" mail is an accepted wart; a custom event-listener SPI keeping a "first password pending" marker is described there too as an alternative, not built: the first-password and later `UPDATE_PASSWORD` events carry identical details, so it needs its own state and tests of Keycloak's transaction behaviour); a password change sends no mail unless the `email` event listener is enabled, and that listener ignores the realm's `eventsEnabled` and `enabledEventTypes` (those only decide which events are *stored*; an empty list stores all): left alone it also mails the owner on every failed login (a mail-bombing vector) and sends two mails per password change, so `docker-compose.yml` restricts it with the server option `KC_SPI_EVENTS_LISTENER__EMAIL__INCLUDE_EVENTS=UPDATE_PASSWORD`; with the lock, an email-only change through the Account API answers 204 and changes nothing (the realm flag's silent ignore) while a name change answers 400, so assert outcomes, not status codes; the dev client's access token has no `auth_time`; Keycloak's own links always point at Keycloak, never at our frontend.
11. **Email change (agreed 2026-10-18; a separate feature, deferred until notification-service exists; full design in `docs/design/03-account-deletion-saga.md` section 10)**: backend-owned, not Keycloak's `UPDATE_EMAIL` (which changes the email inside Keycloak with no state check and no old-address notice). `POST /users/me/email-change` (row lock on the user, 409 unless `ACTIVE`, recent login, one open request per user, random confirm + cancel tokens stored only as hashes, ~30 min expiry; a best-effort availability check outside the transaction: own table, then a Keycloak lookup, taken → 409 `email-unavailable`, Keycloak slow or down → skipped, because Keycloak's public registration already says "Email already exists" so nothing is hidden and the confirm's 409 stays the guarantee) writes outbox commands for notification-service (verification to the new address, notice with a cancel link to the old one) on a dedicated short-retention topic, never `user.events.v1`. The link opens a frontend page that calls `POST .../confirm` (never a `GET` with a side effect): CAS the request `PENDING → APPLYING` for the logged-in owner while the user is `ACTIVE`, Keycloak admin `PUT` email with `emailVerified: true`, with no transaction open during the Keycloak call, then our row + `UserUpdated` + a completion notice; Keycloak 409 → "unavailable"; timeout → `APPLYING` recovery job. The cancel link only cancels a pending request; the completion notice offers "secure my account" (log out sessions, password reset), a full revert is later. Touches the saga in four places only: scheduling cancels the open request, the promoter deletes the user's request rows, confirm applies only while `ACTIVE`, expired rows are purged. Until it exists email is not changeable.
12. **Accepted or open**: no mail to the user when deletion is scheduled until notification-service exists (the login banner is the only notice); `DELETE /me` does not yet require a recent login; PII (emails, names) stays in `user.events.v1` until its retention expires (set `retention.ms` in `kafka-topics.sh` to match the outbox purge, or crypto-shred later); the interceptor and the controller each read the user row (load test, then the TODO in `UserProvisioningInterceptor`); the frontend will need its own public authorization-code + PKCE client; production Keycloak (no `energy-cli`, admin console not public, SMTP, `sslRequired`) is configured when the container step arrives; an admin-initiated deletion is the same state machine with `deletion_scheduled_for = now`. Keycloak's admin events keep the changed data, including email addresses (`adminEventsDetailsEnabled`), and `eventsExpiration` probably does not expire them (unverified): turn the details off or purge them before production. Keycloak's own Account Console (`/realms/energy-tracker/account`, clients `account-console` and `account`) is reachable by every realm user (PKCE does not restrict it; pinned by `KeycloakRealmIT`): the profile lock keeps it harmless, disabling both clients works but needs their full definitions plus the eight account roles in the realm file (a minimal `enabled: false` entry breaks the import) and would turn the four `accountApi_*` tests into 404 tests; open decision, documented in `infra/keycloak/README.md`, as is the prototype login theme that gives the three password pages (register, forgot, change) different titles through `isAppInitiatedAction` and the page message.
